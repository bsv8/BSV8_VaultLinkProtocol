## 1. B 类：阻断项

### B1 Reader 容器状态非栈，嵌套 map 解析失败

`src/proto/cbor.cpp` 的 `Reader` 用**单层**字段（`inMap_`、`mapItemsLeft_`、
`arrItemsLeft_`、`hasLastKey_`、`lastKey_`）跟踪容器，不是按层级的栈。
`EndMap()` 把 `inMap_` 置假并清零 `mapItemsLeft_`，因此**嵌套 map 会破坏外层 map 状态**。

已用真实 `cbor.cpp` 复现：

```
tx body: rawTx(5) network(7) prevouts(8) inputIndex(10)
→ pairs=4; rawTx ok; network ok; prevouts ok
→ 第 4 次 MapKey 失败，ok_=false  ⇒ Prepare() 返回 kMalformed

同一体去掉 inputIndex（pairs=3）→ 全部消费，ok_=true
```

按确定性键序，`inputIndex`(10 字节) 必须排在 `prevouts`(8 字节) 之后，
因此**任何同时携带 `prevouts` 和 `inputIndex` 的 `tx.p2pkh-sign` 请求都会被判为 malformed**，
而省略 `inputIndex` 会静默签第 0 个输入。`secret.open` 侥幸可用，因为 `sealed`(6)
恰好排在 `scope`(5) 之后。`tests/host/test_proto.cpp` 没有任何 map 套 map 的用例，
所以没暴露。

**规范处置**：`spec/core/02-编码.md` 要求 Reader/Writer 的容器状态按层级栈实现，
深度上限 6，嵌套 map/array 为合法且必须支持。见 [0003](./0003-冻结决策.md) D-002。

### B2 `MatchKey.commitment` 从不参与授权匹配

`src/policy/policy.cpp:43-49` 的 `SameScope` 比较
category、operation、protocol、direction、objectHash[16]、sessionId、sessionEpoch、
三个世代字段——**不比较 `commitment[16]`**。而 `src/proto/../ops/dispatch.cpp:844`
明确把承诺前 16 字节写入 `match.commitment`。

这直接违背三处文档：`docs/冻结/线缆格式.md:90-91`（"承诺的前 16 字节进入
`policy::MatchKey`，因此持续授权只覆盖被承诺过的那一个请求"）、
`docs/Keymaster互操作协议草案.md` §2/§6、需求 §5.3。

现状后果：持续授权仅由 `objectHash` 界定。对多数操作 `objectHash` 恰好逐请求唯一
（交易 sighash 前 16 字节、Channel 每条消息摘要、content 摘要前 16 字节），
但承诺本身不提供任何额外约束。

**规范处置**：需求 §6 明确「**单次请求承诺与会话授权范围独立**」，且禁止用整条消息摘要
或整份 commitment 作为唯一持续匹配条件（否则每条消息都重新确认）。因此规范不采用
Rockey 的做法，而是把两件事拆开冻结：

- `requestCommitment` = 覆盖本条请求规范编码的密码学承诺，**仅用于本条请求的绑定与重算比对**；
- `grantScope` = 从实际操作提取的**语义范围**，用于持续授权匹配。

见 [0003](./0003-冻结决策.md) D-005、D-006。

### B3 三个主机世代字段在 MatchKey 中恒为 0

`Prepare` 不设置 `walletGeneration`/`backendGeneration`/`hostRunGeneration`
（只在 `PresentCurrent` 里补 `sessionId`/`sessionEpoch`），这三个字段在所有
`MatchKey` 上都是 0，是永久失效的比较位。世代检查只发生在
`Link::SessionMatch` 的请求准入层。

**规范处置**：规范把世代绑定放进**认证连接与请求信封校验**（不放进 grantScope 的
无效比较位），并规定持续授权在世代变化时必须失效。见 D-006。

### B4 c2s nonce 计数器在解密失败时照常推进

`src/proto/link.cpp:313-314` 先 `BuildNonce(Dir::kC2S, counter_[kC2S]++, nonce)`
再做 AEAD 校验。任何通过 seq 检查但 AEAD 失败的帧都会烧掉一个 counter 值，
导致 c2s nonce 链错位，**之后每一帧都解不开**，主机无法在不重做握手的情况下恢复。
单个被篡改的帧即造成拒绝服务。

重放检查在 `BuildNonce` 之前返回，所以重放帧不烧 counter。

**规范处置**：规范要求计数器**只在认证成功时推进**；任何认证失败必须中止当前连接
（不是继续用错位的链）。见 D-003。

### B5 `secret.seal` 长明文溢栈

`src/ops/dispatch.cpp:1281` 用 `char ctHex[8192]` 承载 `2*(ptLen+16)` 个 hex 字符。
`digest::ToHex` 在 `outCap < len*2+1` 时**返回 0 且不写入**，而调用点忽略返回值。
明文 > 4087 字节时 `ctHex` 保持未初始化内容并作为密文发出。

`Seal` 本身接受明文至 4096 字节（`kPlaintextMax`），与 hex 缓冲上限不一致。

**规范处置**：规范按明文上限与 hex 编码上限分别冻结，并要求编码器对缓冲不足**返回错误
而非静默失败**。见 D-008。

### B6 `check_wire_encoding.py` 的 map 计数检查是死代码

`scripts/check_wire_encoding.py:129` 的出栈条件是
`re.search(r"\bend\b\.?EndMap\(\)", code)`，要求字面量 `end` 出现在 `EndMap()` 之前。
无任何源码行匹配，帧永不弹出，因此 `BeginMap(n)` 的 `n` 与 `Key()` 调用次数从不校验。

已验证：构造 `BeginMap(5)` + 2 次 `Key()` 的文件，该脚本报告无问题。
`src/proto/cbor.cpp` 的 `Writer::BeginMap` 也不记录计数，`EndMap` 只清 `inMap_`，
同样放过 pair 数不符。

**规范处置**：schema 与 conformance 承担这项校验（C++/TS Writer 必须自校验声明的
pair 数）。见 D-001。

### B7 Writer 无法输出嵌套 map

`Writer` 的键序状态是单层且 `BeginMap` 会清 `hasLastKey_`/`lastKey_`，
`EndMap` 不恢复。编码 `{a:1, mm:{zz:9}, aa:2}` 会失败（父层的 `a` 丢失，
`aa` 被拿去与 `zz` 比较）。因此**现有 Writer 只能输出扁平 map**。

同时 `Writer` 完全没有深度限制（`kMaxDepth` 只在 Reader 生效）。

**规范处置**：规范要求 Writer 的容器状态同样按层级栈实现，并要求 Writer 与 Reader
使用同一套键序规则。见 D-002。

## 2. S 类：必须在规范中显式冻结（否则两端实现会分叉）

| 编号 | 事项 | 审计事实 |
| --- | --- | --- |
| S1 | 字节序分裂 | 握手 transcript 用大端 u32（`AppendU32`）；帧 AAD 用 `memcpy` 的**主机本地序**（LE）。同一个 `deviceRunId`/`hostRunGeneration` 在两处以不同字节序出现。 |
| S2 | 帧有效上限 1522 而非 1536 | `ROCKEY_MAX_FRAME_PAYLOAD=1536`，但 `FrameReader` 缓冲 1551 字节而 `Feed` 的守卫是 `len_+15>sizeof(buf)`，实际可收 1522。已验证 plen=1522 通过、1523 丢弃。请求体上限另为 1400。 |
| S3 | `identity.prove`/`authorize` 不要求 challenge/purpose | 无 `have…` 标志。省略 `challenge` 时设备签的是 32 个零字节的声明，仍是"有效请求"。 |
| S4 | 信封键名在 HELLO 与 REQUEST 中不一致 | HELLO 用 `walletGeneration`/`backendGeneration`，REQUEST 用 `walletGen`/`backendGen`。 |
| S5 | `system.info` 声明支持但不可调用 | capabilities 含 `0x0001`，但无 wire 名、无字段解析、无执行器。 |
| S6 | `signatureFormat` 键长 15 而非文档的 25 | 文档 `线缆格式.md:118` 写 `signatureFormat(25)`，实现是 15。 |
| S7 | `migration.import` 的 body 级 `commitment` 被读后丢弃 | 长度校验通过即扔，注释里声称应比对 `SHA256d("rockey:migration:import:v1" ‖ priv)`，实际什么也没算。 |
| S8 | `evidence.receive` 无任何验证 | 能解析、能生成审核文档，`Execute` 直接返回 `unsupported`。无验签、无信任根、无绑定检查。 |
| S9 | `channel.seal` 收 `nonce` 后丢弃；`channel.open` 收 `message` 后忽略 | 主机不可假设两端对称。 |
| S10 | `ValidateScope` 允许空格与 C1 控制符、不校验 UTF-8 | wire 实际限 95 字符（`ExecContext.scope[96]` + `txt()` 的 `n>=cap` 规则），而声明的 `kScopeMax=256` 不可达。 |

| S14 | `BytesNull()` 与零长 bytes 同为 `0x40` | "无负载" 与 "零长负载" 字节相同。 |
| S15 | `Reader::Int()` 对 major 1 且 v ≥ 2^63 是有符号溢出 UB | Writer 产生不了、设备也不接受该输入，但路径未设防。 |

## 5. Keymaster 侧现状

**无任何硬件代码。** 全仓库 `rockey`（忽略大小写）只命中 3 个 Markdown：
`docs/proposals/rockey/Vault软硬件统一需求.md`、`…施工单.md`、`docs/README.md:32`。
`WebSerial`/`navigator.serial`/`SerialPort`/`hid`/`transport` 无实现命中。

主机的密码学出口只有两个（`packages/contracts/src/activeKeyCrypto.ts`）：
`signDigest`（32 字节摘要、DER/compact，无隐式二次 hash）与 `deriveP2pkhAddress`。
Channel、P2PKH、Forum、BitFS 全部叠加在 `signDigest` 之上。这正是 VLP 要消除的
「任意摘要签名绕过业务语义」通路。

Keymaster 的错误码是三套互不相干的体系（Channel 17 个 `ChannelSubscriptionErrorCode`、
`StorageErrorCode` 前缀式、`ProtocolErrorCode`），**没有 Vault 错误枚举**。
VLP 的错误数字码（需求 §5.3 列出的 14 类）是新定义，两端各自映射。
