## 1. 施工原则与依赖

顺序为规格冻结 → 真实向量 → Core/SDK → Profile → 两端接入 → 联合验收 → 发布候选。可以并行整理文档和来源，但没有规格/向量不能把现有 Rockey 行为搬进 SDK 后宣布完成。实现工作以另行授权为前提。

本项目 owns 共同规范/SDK/向量，不替两端完成产品职责。跨仓库任务由各自施工单承担，并带回固定版本的验收证据；本单不自动授权改其它仓库。现有用户改动保留，不回退无关功能。

阶段状态：未开始、实施中、待验证、已验收。勾选表示该项已有可复现证据；阶段门禁全部满足才可宣布阶段通过。规范未定与实现失败分别记录，跳过不是通过。任何并行实现先明确文件/模块责任并协调共享文件，不要求本轮启动并行代理。

## 4. V2：Core 编解码、认证连接及请求状态

责任：本项目 Core；主机/设备两端实现共同规则。

- [ ] 实现有界 CBOR/帧/信封与版本协商，字段必填和完整输入消费、整数精度、深度和长度检查。
- [ ] 实现基于适配 CryptoProvider 的连接、配对、方向密钥、nonce和认证失败状态；套件错误显式阻止业务执行。
- [ ] 实现预期公钥核对及用途隔离的持有权证明；设备编号、USB VID/PID 与主机名称不作身份凭据。
- [ ] 实现单控制连接、App 会话绑定、各运行世代与会话关闭；连接重建时旧队列、决定和结果交付失效。
- [ ] 实现承诺验证、received/queued/awaiting-user/executing/completed 等状态及关联结果，ACK不作为完成。
- [ ] 实现取消/超时/查询/结果未知；缓存淘汰后旧 requestId 仍不二次执行，同 ID 不同承诺拒绝。
- [ ] 实现事件序号、授权修订、锁定/失活清理和执行/交付前复核；丢事件不依赖主机补救设备权限。
- [ ] 实现冻结的单帧或分片模式；控制消息优先且始终认证，分片中断及重连丢弃旧材料。

门禁：真实 Core 在两端完成握手/请求/结果，乱序、篡改、重放、缓存溢出、断包/粘包、断线/旧响应均有可复现负向结果。对应 VLP-01、02、05。

## 7. V5：首批业务 Profile 兼容

责任：VLP负责共同Profile；两端提供真实既有业务样本。

- [ ] Channel：按当前SDK版本固定public/hash/private摘要、签名及seal/open；不同身份A→B/B→A真实往返，不用同设备自封自解替代互通。
- [ ] Channel范围：相同对端/协议/方向的多条合法消息可按已确认范围使用持续决定；换对象/协议/方向或越限重新审核/拒绝，支付不能混入。

- [ ] Profile能力与真实可执行集合一致；Evidence 退出当前范围，未完成 Migration 等操作不出现在已支持集合。
- [ ] 费用池按真实变体/阶段冻结解析器、审核、承诺、授权和向量；Evidence/信用查询任务撤销，参见 B0/B1。
