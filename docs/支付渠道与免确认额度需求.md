# 支付渠道与免确认额度需求

> 日期：2026-10-09。状态：用户确认行为规则；v2 参考实现部分施工，配置同步等 wire 仍待冻结。
> [施工单](./支付渠道与免确认额度施工单.md) · [最小职责需求](./密钥后端最小职责需求.md)。
> 本文优先修正原“软件总是直接执行、硬件每笔确认”的支付行为。业务解释仍归 Keymaster，信用服务不进入设备。

## 1. 渠道注册与共同设置

每个需要花钱的外部 App 或内部插件须向钱包注册支付渠道，每次支付请求携带其渠道信息。当前假定 App/插件可信，不增加第三方信誉认证流程；外部 App 相对可信度低，仍实施会话累计控制。渠道不能跨 owner/App/插件冒用，可信不等于可以自行扩大免确认权限。

同一当前 Key 下软硬后端使用同一逻辑渠道设置。私钥设置页面列出渠道、所属 App/插件、用途、启用状态、单笔免确认额度；App 还可配置新会话默认累计免确认额度。注册不自动授予免确认额度，额度由用户设置。未注册、未启用或未设置有效额度不享受自动支付；缺渠道信息的支付请求拒绝。额度为零表示正金额付款需确认。

最小概念字段：channelId、ownerId/ownerKind（App 或内部插件）、名称/用途、支付类型/网络、enabled、singlePaymentLimit、configRevision；App 另有 defaultSessionLimit。注册字段及身份来源由联合冻结决定，不把申请方文本当授权真值。金额以整数 satoshi 表达，检查精度、非负值及溢出，不经不精确浮点计算。

## 2. 单笔与 App 会话累计额度

内部插件第一版只有单笔额度，不新增其会话/日/月累计额度。外部 App 同时检查单笔与一次连接的会话累计额度。App 一次连接构成会话，绑定 App、当前 Key 与 sessionId；同一 App 会话各渠道花费合并计数，不能换渠道重新获得总额度。这里的累计范围是该 App 会话，不是所有 App 共享的钱包总额。

设本次核验支出为 amount，会话已计入支出及有效预占为 used，单笔额度为 singleLimit，本会话累计额度为 sessionLimit：

| 条件 | 软件 | 硬件 |
| --- | --- | --- |
| 插件 amount <= singleLimit；或 App 同时满足 amount <= singleLimit 且 used + amount <= sessionLimit | 已解锁且现有检查通过后直接执行，不新增额度确认弹窗 | 已解锁且配置/上下文有效时直接执行，不弹交易同意页；实际解析和额度核验仍执行 |
| 超过单笔或 App 会话累计任一额度 | Keymaster 弹窗，用户可同意或拒绝 | 设备显示基础事实和超限原因，由用户实体同意或拒绝 |

额度均是免确认额度，不是禁止付款的硬上限；用户批准后可继续执行超额付款。等于额度属于免确认范围。自动执行不绕过密码/PIN 解锁、App 权限、scope、撤权、实际操作核验、白名单或支持集；配置未知、失效/不同步不得直接自动执行。

支付渠道额度不能被普通“会话允许”绕过，超额的一次批准也不能建立无限自动支付。非支付会话授权规则保留。

## 3. 超额确认与顺手提高额度

显示所属 App/渠道、实际支付对象与金额、单笔额度、会话已支出/本次后累计/当前累计额度以及具体超限原因。提供拒绝、仅批准本次；对于 App 累计超限，还提供“提高本会话累计额度，并批准本次”。输入/选择的新额度需明确展示并经同一批准确认；硬件须在设备查看新值并确认，不能由浏览器点击替代。

仅批准本次不清零累计计数、不自动提高任一额度；随后累计仍超额度时继续逐笔询问。提高只作用于当前 App 会话，不自动提高后续连接默认额度、不提高单笔渠道额度。提高累计额度后，单笔仍超限的后续付款仍询问。当前付款全部超限原因在一次批准中明确展示，不重复弹多个批准框。

此入口不新增“顺手提高单笔额度”；单笔设置通过私钥设置修改。取消批准不执行当前付款；独立改配置/支付失败的提交结果应分别记录，不能显示两者都成功。

## 4. 会话与计数

App 不能自行填报已支出或通过刷新页面、自动重连/新 sessionId 清零。断开结束当前会话；恢复同一业务会话不重置计数，连接恢复还是新建的识别规则在冻结时定义。新会话重新取得用户认可和默认额度，在硬件模式设备明确认可，不能后台无限领取新额度。

软件在钱包执行权威中核算，硬件在设备内核算；主机/页面投影不是计数真值。并发请求须原子检查/预占，跨渠道合并，同一个请求重放不能重复签名或重复扣数。拒绝/确定未执行可释放预占；已生成可花钱签名按承诺支出计入，不等待广播或用广播失败释放额度。结果未知保留占用并查询，不自动退款式清零或重新签署。重启/重连后不能恢复丢失计数的旧会话并继续免确认；恢复状态或使旧会话失效，具体持久/恢复契约需冻结。

额度增大、降低、撤销和请求审批之间要复核 configRevision/会话修订；迟到批准不能作用于新请求或新配置。同 Key 后端迁移不能清零仍可恢复的 App 会话预算并悄悄复用，原会话按既有迁移规则失效。

## 5. 硬件配置同步

Keymaster 提供统一设置入口，硬件保存当前 Key 绑定的渠道、单笔额度、App 默认会话额度、版本/修订等必要配置，按实际操作独立检查。不能只接受主机“额度内”布尔标志。

首次开启免确认、提高单笔或默认会话额度、新会话预算及本会话提高必须经设备实体确认。配置同步有读取/提交/确认状态，主机不能在设备提交前宣称新额度生效。不同步、错 Key/owner、过期版本、损坏或容量超限明确处理，不静默放宽额度。原子持久提交与断电恢复、撤销/降低规则在冻结时定义；在已确认设备配置以外不执行自动支付。

软件也使用经用户确认的同一渠道逻辑配置。软硬迁移保留设置，但硬件首次接受主机现有免确认配置仍须设备认可；不同 Key 注销后旧设置不复活。共同配置不意味着两个活动后端或两个独立计数账本。

## 6. 支出核算与费用池冻结依赖

用户确认只按输出计费，矿工费不计入 amount。普通 P2PKH 为非当前 Key 输出合计，本人找零排除，矿工费仍作为基础交易事实显示。软硬端使用相同整数核算规则。

费用池更新按经核验的本次新增对外付款计入，不每次扣整笔累计金额；矿工费仍不占额度。开池/退款/关池的资金锁定与实际输出归属须逐阶段冻结，不能凭“矿工费不计”推断锁入资金不需审核。完整费用池尚不支持。

新版实现与限制见 [支付与持久状态](../spec/v2/02-支付与持久状态.md)。无电池设备重插须本地解锁、新握手，配置保留、旧 App 会话失效、未知占用不释放；带电池采用相同最小重连规则，见 [断电重连](../spec/v2/03-断电与重连.md)。
