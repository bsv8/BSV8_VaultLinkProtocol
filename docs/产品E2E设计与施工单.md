# RocKey / Keymaster 产品 E2E 设计与施工单

日期：2026-10-10。范围：验证已经确定的业务，不增加钱包业务或 VLP 消息类型。

## 验证边界

已有 SDK ESP32 示例测试仍验证 SDK；本入口必须运行 RocKey 的 `src/core/app.cpp`、实际 Controller、KeyStore、支付策略、密码学与 LittleFS。不能用示例固件代替产品固件。

```text
测试控制 → 有界按键电平 → 正常 Buttons/UI ─┐
实体三按钮 ───────────→ 正常 Buttons/UI ─┴→ Controller / KeyStore / 支付策略
                                             ↕ VLP 加密帧
浏览器 Web Serial → 正式 Window USB bridge → MessagePort → Keymaster Worker
                                                        → 正式连接所有者与付款服务
```

测试控制只能选择固定公开测试密钥、观察非秘密状态、注入 A/B/C 电平及重启。没有直接解锁、任意私钥、任意摘要签名、直接批准或清空额度接口。自动确认实际执行滚动、短按/长按和松键栅栏。测试 PIN 固定为八个 `0`，经正常 PIN 页输入；主机不能通过业务协议发送 PIN。

Keymaster E2E 使用真实 Worker 中的 HardwareConnectionOwner、WorkerUsbTransport、VaultLinkHardwareBackend 和 HardwareWalletPayments，Window 使用正式 openWindowUsbBridge。独立测试装配不进入正常 App，也不假装已经验证整个 Keymaster 设置/发送页面。那些页面的真机操作列入最终人工验收。

## 测试专用 USB 外层

M5Stack USB 转串口只有一条数据流。测试固件将原样 VLP 字节与测试控制分帧复用，避免串口日志或控制文本插入加密帧。

| 字段 | 长度 | 内容 |
| --- | --- | --- |
| magic | 4 | ASCII `RKET` |
| kind | 1 | 1=VLP 字节，2=测试命令，3=测试回复 |
| id | 4 | 小端；VLP 为 0，测试命令/回复使用非零关联编号 |
| size | 2 | 小端；最多 4096 字节 |
| payload | size | VLP 原始字节，或命令/CBOR 回复 |
| CRC32 | 4 | 小端；覆盖 magic 到 payload，标准 IEEE CRC32 |

测试命令载荷：`[1]` 读状态；`[2,button,down,ttlLo,ttlHi]` 设置按钮电平；`[3]` 首次注入固定公开测试密钥；`[4]` 500ms 后重启。按钮 A/B/C=0/1/2，down=0/1，按下期限 30–4000ms；期限到自动松键，断线不能留下无限长按。

状态只给固件/构建号、隔离标志、公钥、锁定状态、PIN 失败次数与等待、屏幕/光标/已输入位数、审核操作、阅读位置和审核次数；不返回已输入 PIN、私钥或软件密码封装。配对码是公开 UI 内容，测试比较两端实际值。

这层复用只存在测试构建；它不是正式 VLP 协议扩展。正式固件仍直接收发最简 VLP。SDK 公共导出和两个项目固定的 SDK 副本不因此变化。

## 存储与刷机

测试构建强制 `ROCKEY_E2E_ISOLATED`，实际 store API 将路径映射到 `/e2e/vault` 和 `/e2e/docs`。使用相同 LittleFS、CRC、原子 rename 与 PIN 封装实现，不读取或覆盖正式 `/vault`。已有测试钱包不是固定测试公钥时拒绝覆盖。

刷机入口要求明确物理串口，不以 CP2104 VID/PID 推断钱包身份。先备份完整 4MiB Flash 到仓库外私有目录，目录 0700、文件 0600。报告不包含备份内容。分区表与已备份设备不一致时拒绝上传；只在用户明确确认空的专用测试设备时使用 `--initialize-empty-test-device` 建立 LittleFS。日后升级不格式化文件系统，不执行整片擦除，不烧 eFuse。

测试固件和正式固件用不同构建环境。发布 ELF 扫描必须确认测试控制、测试私钥和模拟输入符号不存在；同一扫描对测试 ELF 必须失败。

## 自动真机检查

22 项检查使用真实 USB、设备屏幕状态与真实签名验签：

1. 错 PIN 失败落盘、重启不清零、正常解锁。
2. 设备否决配对时 Keymaster 注册失败。
3. 双端配对码一致、Worker 持有权验证及身份登记。
4. 产品固件、自检、隔离目录与固定公钥。
5. App 两个渠道、内部插件渠道注册和配置需要设备确认。
6. 缺渠道编号或未注册渠道拒绝签名。
7. App 本次连接会话总额确认。
8. 单笔/会话额度内自动签名，无审核页。
9. 两个渠道共享同一会话总额，等于上限免确认。
10. 超会话总额否决后无签名、无扣额。
11. 超会话总额仅批准本次，不改变上限。
12. 确认时提高当前会话总额，不改变下一次默认限额。
13. 插件只有单笔上限，累计两笔不新增总额限制。
14. 已完成 paymentId 不重复签名。
15. 插件超单笔限额先否决、再批准不同请求。
16. 未读完不能确认；读完后短按 B 也不能确认。
17. 取消等待中的 App 支付，审核页撤下，额度保持。
18. 标准 BSV 签名路径。
19. Connect 费用池 Funding 与累计支付增量。
20. BitFS 费用池 Funding 与累计支付增量。
21. 关闭 App 会话保留累计，关闭后拒绝支付。
22. ESP32 软件重启后渠道配置与已关闭会话累计保留。

交易是本地构造并经过实际解析/签名/验签的离线证据，不广播，也不宣称完成链上支付。每次运行的新会话和 paymentId 独立，已有账本不自动清空。

## 最终人工门禁

自动注入不证明按键电气质量、屏幕可读性或真实断电行为。以下保持待验收：

- 正式固件在完整 Keymaster App 中连接、配对、注册渠道、发送与超额确认/否决。
- 三实体按钮短按/长按、长文滚动、PIN 修改、错误等待和取消；关闭测试入口仍可操作。
- 实际掉电发生在额度预占、签名后回复前和存储提交期间，检查 unknown/保留额度，不能以 `ESP.restart()` 冒充断电。
- 双向迁移：同一 Key 身份/数据/完整账本保留；迁回软件先成功提交浏览器，再设备重新 PIN 和独立擦除。已有原生迁移用例作为自动前置门禁，真机迁移另验收。
- 费用池特有授权/退款阶段及其它支持的签名 Profile：沿用原生回归，真机屏幕与按钮验收后才能记完整支持集通过。
