# Migration Profile

> VLP 0.1 Draft · profileId `migration` · profileVersion `0.1`
> 决策见 [D-012](../../decisions/0003-冻结决策.md)。

## 1. 范围

**同 Key** 的导入与迁回、进度查询、持有权与兼容证明。
使用**设备专用状态**，不开放普通 App 的私钥导出。

迁移保持原业务 Key、公钥和既有数据密码学兼容（需求 §1）。

## 2. 生命周期区分

| 场景 | 语义 |
| --- | --- |
| **同 Key 迁移** | 保留身份与数据，推进后端及会话世代 |
| **不同 Key 替换** | 在 Keymaster 注销并删除旧钱包数据后创建/导入 |

两者是**不同的生命周期**。VLP 只提供绑定与失效契约；
数据库删除由产品执行。

## 3. 阶段

```
host-prepared → device-staged → device-committed → host-committed → cleaned
```

| 阶段 | 含义 |
| --- | --- |
| `host-prepared` | 主机冻结待导入材料 |
| `device-staged` | 设备已接收并校验，尚未持久提交 |
| `device-committed` | 设备内部封装**持久**完成 |
| `host-committed` | 主机绑定提交完成 |
| `cleaned` | 旧软件活动材料移除 |

**设备提交与主机提交不宣称跨设备原子。** 每个边界可恢复查询。

## 4. 操作

### 4.1 `migration.import`

| 序 | 键 | 键长 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- | --- | --- |
| 1 | `op` | 2 | text | 是 | `"migration.import"` |
| 2 | `opVersion` | 9 | u32 | 是 | = 1 |
| 3 | `privKey` | 7 | bytes | **是** | 恰好 32，有效 secp256k1 标量 |
| 4 | `commitment` | 10 | bytes | **是** | 恰好 32，见 §4.2 |

键序：`op(2) < privKey(7) < commitment(10) < opVersion(9)` 按长度优先再字节序
实际为 `op(2) < privKey(7) < opVersion(9) < commitment(10)`。

> 现有实现把 body 里的 `commitment` 长度校验后**直接丢弃**，
> 且注释声称应比对但实际什么也没算
> ——[0002](../../decisions/0002-差异清单.md) §2 S7。VLP 要求**真正比对**。

### 4.2 导入承诺

```
importCommitment = SHA256d("vlp:migration:import:v1" || 0x00 || privKey)
```

域标签 23 字节；构造输入 23 + 1 + 32 = 56 字节。

设备**重算并比较**。不符 → `invalid-request`。

这把导入材料绑定到一条具体请求，防止重放旧的导入承诺。

### 4.3 `migration.status`

请求体只有 `op` 与 `opVersion`。

结果：map(1)，键序 `record`(6) text，格式
`"<stage>|<direction>|<publicKeyHex>|<migrationId>"`，无记录时为 `"<stage>|<0>"`。

公开字段含 `migrationId`、公钥、方向与格式版本，**不含私钥/PIN/密码**。

### 4.4 `migration.export`

**仅**在设备菜单进入后由内部流程调用，**一次性确认**。

| 规则 | 内容 |
| --- | --- |
| 普通 App | **不能**调用私钥导出 |
| 持续允许 | **不能**调用私钥导出 |
| 确认方式 | **设备专用一次性确认**（物理），不可由 SDK 或持续授权代替 |
| 单次有效 | 确认后一次性有效，用后即失效 |

## 5. 未初始化设备

```
1  实体配对完成（迁移专用连接）
2  接收 import
3  导入并持久提交
4  导入完成后才证明持有业务身份
```

**设备未初始化时不得因「必须先有 Key」而无法导入。**
迁移专用连接在实体配对后即可接收导入。
**不以生成新 Key 代替迁移。**

普通业务在未初始化状态下**仍需身份验证**（[04-握手与链路](../core/04-握手与链路.md) §6）。

## 6. 冲突与恢复

| 规则 | 内容 |
| --- | --- |
| 查询 | 每个阶段都可查询 |
| 恢复 | 每个提交点的中断都可恢复 |
| 重试 | **同一** `migrationId` 重试**不重复覆盖** |
| 冲突 | 不同 `migrationId` 并发 → `migration-conflict` |
| 并行 | 迁移期间**不并行批准**两后端业务 |
| 未完成 | 保持受限模式 |

### 6.1 提交顺序与恢复

| 边界 | 状态 | 恢复方向 |
| --- | --- | --- |
| 主机冻结后、设备提交前 | `host-prepared` | 主机可放弃或重试 |
| 设备已接收未提交 | `device-staged` | 断电后设备无有效封装，可重试 |
| 设备已持久提交、主机未提交 | `device-committed` | 主机必须能查询到并完成提交 |
| 主机已提交 | `host-committed` | **无自动软件回退** |
| 旧材料已移除 | `cleaned` | 终态 |

**主机提交前保留软件可恢复记录**；提交后无自动回退。

**PIN/封装中断不破坏已提交旧封装。**

### 6.2 硬迁软方向

先验证并提交新的软件封装，**再**处理设备副本。
**不能先擦掉唯一可恢复材料。**

## 7. 副本与擦除策略（未定）

| 项 | 状态 |
| --- | --- |
| 是否在设备保留旧软件封装作为默认建议 | **未定**——待产品确认 |
| 最终副本策略 | **未定** |
| 擦除策略 | **未定** |

**未确认的策略保留未定，本规范不擅自删除唯一副本。**

浏览器注销**不自动擦设备**。物理擦除由**设备专用确认**触发。

恢复备份的格式与恢复 UI 属于**产品验收**，不由本规范伪称完成。

## 8. 无秘密

公开的 journal、日志与结果**不含**私钥、PIN 或密码。

迁回软件后必须明确告知**私钥已进入软件环境**。
浏览器注销**不触发自动擦除**。

## 9. 负向向量（必须确定失败）

| 情形 | 期望 |
| --- | --- |
| 换 `privKey` 保留旧 `commitment` | `invalid-request` |
| `commitment` 全零 | `invalid-request` |
| 普通 App 请求导出 | `unsupported` / `denied-once` |
| 持续允许状态下请求导出 | `unsupported`（导出不在任何持续范围内） |
| 并发两个不同 `migrationId` | `migration-conflict` |
| 同 `migrationId` 重试 | 幂等，**不重复覆盖** |
| `privKey` 不是有效标量 | `invalid-request` |
| 未完成迁移时请求普通业务 | 受限模式，按 [04](../core/04-握手与链路.md) §2.3 处理 |
