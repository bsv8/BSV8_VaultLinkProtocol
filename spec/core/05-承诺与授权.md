# 05 承诺与授权范围

> VLP 0.1 Draft · 决策见 [D-005](../../decisions/0003-冻结决策.md)、
> [D-006](../../decisions/0003-冻结决策.md)、[D-007](../../decisions/0003-冻结决策.md)。
> 相关差异见 [0002](../../decisions/0002-差异清单.md) §1 B2/B3。

## 1. 两个对象，两件事

需求 §6 的核心区分，本规范具体化为**互不替代**的两个对象：

| 对象 | 回答的问题 | 唯一性 | 用途 |
| --- | --- | --- | --- |
| `requestCommitment` | **这一条**请求主机承诺了什么 | 逐请求唯一 | 本条请求的绑定、结果关联、拒绝重放 |
| `grantScope` | 用户批准的**范围**是什么 | 多条请求可共用 | 持续决定的匹配 |

**禁止**把整条消息摘要或整份 commitment 当作持续授权的唯一匹配条件——
那会让每条消息都重新确认，等于没有持续授权。
**也禁止**用 `grantScope` 代替承诺——那会让不同对象共用一条授权。

## 2. requestCommitment

### 2.1 构造

```
requestCommitment = SHA256d(
    "vlp:commit:v1"      UTF-8, 13 字节, 无 NUL
 || 0x00
 || profileId            UTF-8, 无 NUL
 || 0x00
 || profileVersion       u8
 || 规范对象编码          见 §2.3
)
```

`SHA256d` = SHA256(SHA256(x))。

### 2.2 规则

| 规则 | 内容 |
| --- | --- |
| 必填 | 32 字节；缺失或全零 → `invalid-request` |
| 设备重算 | 设备**重算并比较**。必填与非零检查**不能**替代重算 |
| 字段集合 | 由**各 Profile 固定**（§2.3）。主机不得挑选 |
| 不跨请求 | 同 `requestId` 不同承诺 → 拒绝 |
| 结果关联 | 结果必须绑定该承诺 |

### 2.3 各 Profile 承诺覆盖

「规范对象编码」指该 Profile 的**核心对象**的 `VLP-CBOR-1` 编码，
逐 Profile 定义在 [spec/profiles/](../profiles/00-通用约定.md)。覆盖三类内容：

1. **实际操作**——将被签名/加密/解封的字节本身；
2. **安全相关证据**——网络、金额、前序、输入归属、接收公钥、范围参数；
3. **显示内容**——设备将展示的关键字段（名称、地址、协议、对端、用途）。

**主机不能自行决定覆盖哪些字段。** 设备按 Profile 固定规则重算。

## 3. grantScope

### 3.1 结构

```
grantScope = {
  category,        u8   （[04](./04-握手与链路.md) §2.4）
  profileId,       text
  profileVersion,  u8
  operation,       u8
  peerPublicKey,   bytes 33 或 null
  protocolId,      u8   （已登记协议；未登记直接拒绝，不降级为"无协议"）
  direction,       u8   （0 none / 1 inbound / 2 outbound）
  sessionId,       u32
  sessionEpoch,    u8
  limits,          map   （见 §5）
}
```

### 3.2 提取规则

| 规则 | 内容 |
| --- | --- |
| 来源 | **设备从实际操作提取**。主机自报的 `grantId` 一律不信 |
| 对端 | `channel.seal` 只接受 `recipientPub`；`channel.open` 只接受 `senderPub`；交叉填写直接拒绝 |
| 协议 | 已登记协议名确定性映射到 `protocolId`；未登记 → 拒绝 |
| 方向 | seal = outbound；open/public/hash/private = inbound |
| 对象 | **不包含**逐请求的消息摘要——否则每条消息都要重新确认 |
| 世代 | **不放进 grantScope**。世代变化时清空全部持续决定（§4.3） |

### 3.3 语义范围（哪些操作能被持续授权覆盖）

| 类别 | 持续允许可覆盖 | 不可覆盖 |
| --- | --- | --- |
| CHANNEL | 同对端、同协议、同方向的多条合法消息 | 支付、导出、擦除 |
| LOCAL_SECRET | 同 `scope` | 跨 scope；长期派生密钥导出 |
| IDENTITY | 无（每次重新确认） | — |
| TRANSACTION | 无（每次重新确认） | — |
| CONTENT | 无（每次重新确认） | — |
| MIGRATION | 无 | 一切 |
| EVIDENCE | 无（未冻结） | — |

**没有语义解析器的消息不自动获得宽范围授权。**
若设备不能把消息解析为已知 Profile 对象，则该消息**不产生** `grantScope`，
必须逐次确认。

## 4. 决定状态机

### 4.1 决定

| 值 | 决定 | 作用域 |
| --- | --- | --- |
| 0 | `undecided` | — |
| 1 | `allow-once` | 仅本条 |
| 2 | `deny-once` | 仅本条 |
| 3 | `allow-session` | 匹配 `grantScope` 的后续请求 |
| 4 | `deny-session` | 匹配 `grantScope` 的后续请求 |

### 4.2 求值

```
查找与 grantScope 完全匹配的持续决定（范围重叠时取更窄者）

无匹配                    → need-user（弹窗）
匹配且为 deny-session      → denied      （直接拒绝，不再弹窗）
匹配且为 allow-session     → 检查限额
  超次数或超金额           → exhausted   （必须重新授权）
  否则                    → allowed     （直接执行，不弹窗）
```

**否决优先于允许。** 命中持续否决时**直接拒绝，不反复弹窗**。

范围重叠且同时存在 allow 与 deny 时：**deny 生效**，
不因更宽的 allow 而放行。

### 4.3 失效与推进 `decisionRevision`

以下任一发生时，**清空全部持续决定**并推进 `decisionRevision`：

| 触发 | 说明 |
| --- | --- |
| `hostRunGeneration` 变化 | 主机重启 |
| `walletGeneration` 变化 | 钱包注销重建 |
| `backendGeneration` 变化 | **同 Key 迁移也必不同** |
| `deviceRunId` / `connectionId` 变化 | 设备重启或连接重建 |
| 锁定 / 断线 / 失活 / 会话关闭 | |
| 用户取消任一持续决定 | 回到 `undecided` |

**持续决定不落盘**，重启后一律 `undecided`。
PIN 失败计数与迁移状态可落盘。

### 4.4 取消

设备本地可取消**任一**持续决定；取消后该槽位回到 `undecided`，
`decisionRevision` 推进，下一条匹配请求必须**重新询问**。

持续决定表在 VLP 0.1 固定 **8** 条；满时新的持续决定请求返回 `busy`，
不覆盖已有条目。

## 5. 限额

### 5.1 结构

```
limits = {
  maxCount,     u32   （0 = 不限次数）
  budgetSats,   u64   （0 = 不限金额）
}
```

### 5.2 判定与消耗

| 时点 | 动作 |
| --- | --- |
| **请求到达时** | `spentSats + 本次金额 > budgetSats` → 超限，重新授权 |
| 边界 | 恰好等于预算**允许**（`>` 而非 `>=`） |
| **执行成功后**、交付结果前 | `usedCount += 1`；`spentSats += 本次金额` |
| 溢出 | 累加前检查 `a > UINT64_MAX − b`；溢出视为超限拒绝，**不回绕** |
| 金额 | 一律 satoshi u64；`bsv.p2pkh-sign` 取设备自算的支付总额 |

**授权后执行失败不扣预算**（消耗在执行成功之后）。

## 6. 执行前复核

设备在**真正执行前**必须重新求值：

```
revision 未变 且 仍为 allowed        → 执行
revision 变了 且 变为 undecided     → 回到待确认，**重新询问，不执行**
命中 deny-session                  → revoked，不执行
```

主机在**交付结果前**再次检查自身权限（两端权限均须成立）。

## 7. 授权与执行的顺序

```
解析请求（含未知键/必填/上限检查）
  → 提取 grantScope 与 commitment 覆盖对象
  → 重算 requestCommitment，不符 → invalid-request
  → 生成结构化审核对象（内容在此冻结，审核期间不变）
  → 按 §4.2 求值
      need-user → 询问用户 → 记录决定 → 执行
      allowed   → 直接执行
      denied    → 直接拒绝
  → 按 §5.2 消耗限额
  → 执行前按 §6 复核
  → 执行并交付结果
```

**审核期间内容冻结**；若内容变更则取消旧请求并重新审核。
