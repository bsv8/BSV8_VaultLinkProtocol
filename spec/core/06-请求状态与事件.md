# 06 请求状态与事件

> VLP 0.1 Draft · 决策见 [D-011](../../decisions/0003-冻结决策.md)。
> 授权语义见 [05-承诺与授权.md](./05-承诺与授权.md)；错误码见
> [07-错误码.md](./07-错误码.md)。

## 1. 请求状态

| 值 | 状态 | 含义 |
| --- | --- | --- |
| 0 | `received` | 已接收，尚未解析 |
| 1 | `queued` | 解析通过，排队等待处理 |
| 2 | `awaiting-user` | 等待用户确认 |
| 3 | `executing` | 执行中 |
| 4 | `completed` | 执行完成 |
| 5 | `denied` | 用户拒绝 |
| 6 | `cancelled` | 已取消 |
| 7 | `expired` | 超时失效 |
| 8 | `unknown` | **主机无法确定**执行结果 |

### 1.1 状态迁移

```
received → queued → awaiting-user → executing → completed
              │            │             │
              │            ↓             ↓
              │        denied/cancelled  denied
              ↓
        denied / cancelled / expired
```

- `completed`/`denied`/`cancelled`/`expired` 为终态。
- `executing` 之后**不承诺撤回**已产生的签名或广播。
- `unknown` 只存在于**主机侧**：主机丢失结果且无法查询判定。

### 1.2 ACK 不是完成

传输层 `ACK_REQUIRED` 的确认**只表示字节已收到**。
`queued` 与 `awaiting-user` 都**不是**成功。SDK 的 `execute` 只在
`completed` 时返回成功。

## 2. 结果查询

`QUERY`（`0x13`）→ `QUERY_RESULT`（`0x14`）：

| 消息 | 键序 | 值 |
| --- | --- | --- |
| `QUERY` | map(1) | `requestId`(9) u32 |
| `QUERY_RESULT` | map(3) | `state`(5) u32；`requestId`(9) u32；`payload`(7) bytes 或 `null` |

查询结果必须与提交时的 `requestCommitment` 一致，否则 `invalid-request`。

**主机结果未知时状态为 `unknown`，不得推断成功，也不得自动重发。**
自动重发可能造成重复支付。

## 3. 防重放与结果缓存

### 3.1 序列检查

| 方向 | 规则 |
| --- | --- |
| c2s | `seq` **严格递增**（首帧任意值）；`seq <= 已见` → `replay` |
| s2c | 同上 |
| 更新时机 | **只在认证成功后**更新已见序号 |

### 3.2 请求去重

| 情形 | 结果 |
| --- | --- |
| 同 `requestId` 仍在处理中 | `busy`，**不二次执行** |
| 同 `requestId` 已完成且承诺相同 | 返回缓存结果，**不二次执行** |
| 同 `requestId` 已完成但**承诺不同** | 拒绝，`invalid-request` |
| 缓存已满 | `busy` |

**结果缓存满时不淘汰。** 淘汰会让被淘汰的 `requestId` 再次出现时被当作新请求执行，
违反 VLP-05。因此 VLP 0.1 的行为是返回 `busy`。

> 这与现有实现一致，是审计中少数正确保留的行为。

### 3.3 结果缓存规模

| 项 | 值 |
| --- | --- |
| 缓存条目数 | 8 |
| 淘汰策略 | **无**（见 §3.2） |
| 清除时机 | 锁定、断开、迁移、重启、会话关闭 |

## 4. 事件

### 4.1 事件类型

| 值 | `kind` | 键序 | 说明 |
| --- | --- | --- | --- |
| 0 | `request-state` | `kind(4) < state(5) < requestId(9)` | 请求状态变更 |
| 1 | `device-state` | `kind(4) < sessionId(9) < deviceState(11)` | 设备锁定/解锁/会话变化 |
| 2 | `auth-revision` | `kind(4) < decisionRevision(14)` | 授权修订推进（撤销/取消） |
| 3 | `session-closed` | `kind(4) < reason(6) < sessionId(9)` | 会话结束 |

事件帧外层见 [03-帧与消息.md](./03-帧与消息.md) §7
（`payload` / `eventSeq` / `deviceRunId`）。

### 4.2 规则

| 规则 | 内容 |
| --- | --- |
| 单调 | `eventSeq` 在运行世代内从 1 单调递增 |
| 旧事件 | 主机**忽略** `eventSeq` 小于已见最大值的旧事件 |
| **丢失不使撤权失效** | 撤权在设备侧即时生效；主机交付前自行复查权限 |
| 事件丢失 | **不依赖**主机补救设备权限 |
| 顺序 | 事件只反映设备侧状态；主机不得据此推断执行结果 |

## 5. 取消

| 规则 | 内容 |
| --- | --- |
| 通道 | `CANCEL` 标志，走独立优先级，但**始终认证** |
| 保证范围 | **只对尚未执行者**保证未执行 |
| 已执行 | 已签或已广播**不承诺撤回**；返回实际状态 |
| 未知 | 若设备无法确定是否已执行，返回 `result-unknown`，**不假装取消成功** |
| 关联 | 取消必须携带 `requestId` 与承诺 |

## 6. 队列与超时

### 6.1 队列额度

| 项 | 值 | 说明 |
| --- | --- | --- |
| 待处理请求队列深度 | **4** | 满时返回 `busy`，**不排队等待** |
| 结果缓存条目数 | **8** | 满时返回 `busy`，**不淘汰**（§3.2） |
| 同时开放会话数 | **2** | 设备侧上限 |
| 持续决定条目数 | **8** | 满时新的持续决定返回 `busy` |

队列深度是有界资源：设备**不得**按主机自报的期望深度分配内存。

### 6.2 超时

| 项 | 值 | 结果 |
| --- | --- | --- |
| 请求 TTL | 120000 ms | `expired` / `timeout` |
| 队列等待 | 计入同一 TTL | 过期项失效，不得执行 |

队列中的请求过期时必须失效，**不得静默消失**——主机需要收到终态或通过查询得知。

## 7. 锁定与撤权清理

以下动作**必须**清空持续决定、清空队列、使旧结果交付失效：

| 动作 |
| --- |
| 设备锁定 / 解锁 |
| 链路断开或失活超时 |
| 会话关闭 |
| 迁移开始或完成 |
| 设备重启 |
| 用户撤销任一持续决定 |

**清除后到达的旧 `eventSeq` 与旧结果一律丢弃。**
