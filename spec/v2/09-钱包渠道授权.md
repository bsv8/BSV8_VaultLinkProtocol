# 钱包渠道授权（产品 Draft 0x234）

USB 最简三消息、加密、实体配对和 wire 2 不变。本增量收口业务签名与钱包策略的权限边界。下面的新约定优先于早期网络身份及支付规范中由主机配置硬件、Peer Record 采用临时 ScopeGrants 的描述。

## 身份与注册

钱包身份是先确定的 `bsvNetwork: main | test` 加 33 字节压缩 secp256k1 公钥。主机不能用注册请求变更身份。

签名渠道记录严格六字段：

```text
{id: tstr, owner: tstr, kind: "app" | "plugin",
 operation: tstr, mode: "automatic" | "manual", revision: uint32}
```

id、owner 使用现有钱包标识符规则：1..96 个 ASCII 字符，允许字母、数字、`.`、`_`、`:`、`/`、`-`。revision 从 1 开始，小于 0xffffffff。每个钱包最多 32 个非支付签名渠道；支付渠道继续受既有独立容量限制。同一次注册批次不允许重复编号。

| operation | profile v1 | 严格 body |
|---|---|---|
| signing.register | signing-register | `{network:tstr, channels:[渠道记录...]}` |
| signing.list | signing-list | `{}` |
| signing.execute | signing-request | `{channelId:tstr, operation:tstr, body:原Profile正文, commitment:bstr(32)}` |

register 的 channels 非空，最多 32 项。首次新增渠道需钱包用户确认建议，已存在的编号只核对 owner/kind/operation，忽略建议 mode/revision，返回钱包当前记录。来源冲突拒绝，任何主机请求均不能覆盖实际模式。返回 `{channels:[当前全部渠道记录...]}`。list 返回相同字段，为只读。

execute 外层请求承诺由 signing-request/v1 和完整外层 body 生成。设备先核对注册编号与操作，随后按原 Profile 重建、解析、校验内层完整正文及内层承诺；不是把主机摘要交给私钥。系统查询和取消必须使用外层实际请求 ID 与外层承诺。结果沿用内层 Profile 的结果格式。

未注册、操作不匹配、取消、锁定、失效身份或设置修订变化均不得签名。mode=automatic 不展示人工授权页；mode=manual 必须取得用户的当次决定。等待期间该渠道 revision 改变，旧批准失效。

## 支持集与边界

已接通的硬件非支付签名为 identity.noise-proof、identity.peer-record、connect.identity-sign、connect.intent-sign、bitfs.wire-sign，以及 channel.public-message、channel.hash-request、channel.private-message。各操作的原正文限制继续生效。BitFS 涉金额的 Kind 5 继续要求实际支付上下文。软件还登记 software.digest-sign；硬件不提供该执行 Profile。

Noise 和 Peer Record 是独立渠道，初次建议自动；其余初次建议人工。用户可在钱包内部修改。配对身份持有权证明、PIN、密钥迁移证明/导出/擦除保持各自独立安全流程，不得借业务渠道自动批准。

支付仍使用既有渠道编号与支付账本，不通过非支付 execute 绕过真实金额解析和预占。`payment.configure` 的现有 wire 名称在本 Draft 仅用于首次注册建议；已有渠道只返回实际 revision，不接受主机修改。RocKey 的模式、单笔上限和 App 默认累计额度只能在本机菜单修改。软件内部配置能力不等于硬件 USB 配置能力。

App 的累计额度按 owner 和已持久会话计算，跨支付渠道合计。超额不是硬拒绝：用户可以批准当次，或在确认时提高当前会话上限。未来默认上限与当前会话增额是不同操作。

## bank v4

采用原 v3 账本字段与归档规则，加上 `network` 和 `signing`：

```text
{version:4, key:tstr, network:"main"|"test", signing:[渠道记录...],
 channels:[支付渠道...], sessions:[含 archivedUsed 的会话...],
 pending:[原支付记录...], pools:[含 archivedPaid 的费用池...],
 archive:{payments:[原墓碑...],sessions:[原会话墓碑...]}}
```

整数保留 uint64，承诺及归档哈希保持 bstr。CBOR 规范键序与原限制一致，总 bank 不超过 65536 字节。签名渠道与支付账本原子提交，一起参与 migration policyHash；迁移连续性检查不允许删除渠道、改来源或倒退修订。软件储存根和设备 KeyStore 的网络身份必须与 bank.network 相同。

已有 v2/v3 bank 保留读取及数据升级；首次新增签名渠道升级至 v4，补齐空归档及已有会话/池的 archivedUsed/archivedPaid，不清空记录。硬件 SDK 与软件 SDK 使用同一规则。

## 网络签名等待

Keymaster 为一个 Host 的固定 Noise 静态公钥先申请签名，完成后才创建网络 Host；关闭 Host 后擦掉种子与证明，下一 Host 重新申请。已有签名的重用不构成再次私钥签名，改变策略不会撤销已经产生的签名或已经建立的连接。

Peer Record 的完整正文及 sequence 仍先 seal（取得签名）再 push；不预签未知记录。人工等待使用钱包操作 TTL 和独立取消，不使用原 libp2p 的 5 秒签名计时提前结束 UI。业务网络超时仍适用于真正的网络阶段。
