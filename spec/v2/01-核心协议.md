# VLP 0.2 Draft / wire 2：已实施的最小核心

日期：2026-10-09。实现位于 `Coding/BSV8_VaultLinkProtocol`。本文记录本轮实际 wire；旧 `spec/core`、`schemas/*.json` 和旧 conformance 属于 0.1，不能混用或据此声明新版全能力兼容。0.2 尚不是发布标准。

## 帧与密码

帧依次为：magic `a5 5a`、version u8=2、type u8、flags u8=0、seq u32LE、payloadLength u16LE、payload、CRC32 u32LE。CRC 覆盖 version 至 payload，仅负责传输误码；身份/完整性由认证加密负责。负载最多 1024 字节，总帧最多 1039。单条认证记录的规范 CBOR 明文最多 896 字节；更大的业务信封按下述有界规则分片。

| type | 名称 | 内容 |
| --- | --- | --- |
| 1 / 2 | HELLO / HELLO_ACK | 明文规范 CBOR，seq=0 |
| 3 / 4 | PAIR_CONFIRM / PAIR_OK | 加密配对确认 |
| 5 / 6 | POSSESSION_PROVE / POSSESSION_OK | 加密挑战与当前 Key 持有权证明 |
| 16 / 17 / 18 | REQUEST / RESPONSE / EVENT | 加密业务与控制 |

仅固定 X25519 + HKDF-SHA256 + AES-256-GCM。握手双方每连接新生成临时密钥、32 字节 nonce；钱包长期 secp256k1 私钥只用于受限持有权证明及已登记签名，不用于 USB 密钥协商。

HELLO 必有 `hostEph:bstr32, hostNonce:bstr32, protocolVersion:2, capabilities:uint[], walletGeneration:uint32, backendGeneration:uint32, hostRunGeneration:uint32`。ACK 必有 `deviceEph:bstr32, deviceNonce:bstr32, publicKey:bstr33, deviceRunId:uint32, connectionId:uint32, protocolVersion:2, capabilities:uint[]`。所有 generation/ID 非零；能力最多 32、不重复。参考能力编号 `0x221`、原产品支付能力 `0x222`、含费用池的产品支付能力 `0x223`、增加标准单钥输入和有界业务分片的产品能力 `0x224`、包含 v3 本地秘密操作的产品能力 `0x225`、包含本地秘密持续决定与设备撤销菜单的产品能力 `0x226`、包含 App 预算恢复/指定关闭与渠道列表的产品能力 `0x227`、包含 Connect 完整身份/意图信封签名的产品能力 `0x228`、增加 Channel 完整消息签名和收件箱封装/解封的产品能力 `0x229`、增加 BitFS 原文消息签名的产品能力 `0x22a`、把 BitFS Kind 5 付款授权纳入金额核心的产品能力 `0x22b`、增加受限网络身份签名的产品能力 `0x22c`、增加 BitFS 卖方 Kind 2 开池预签的产品能力 `0x22d`、增加公开付款账本分块导出的产品能力 `0x22e`、增加公开迁移 journal 的产品能力 `0x22f`、增加本地开启/重新 PIN 的硬迁软导出与独立擦除的产品能力 `0x230`、旧 Key 已不存在时仅恢复公开回执的受限能力 `0x231` 仅供草案集成，协商值不能替代操作注册和真实支持检查。

transcript = SHA256(`UTF8("vlp:handshake:v2\0") || canonicalCBOR({hello,ack})`)；整个握手对象均绑定。方向密钥及 baseNonce 分别以 sharedSecret 为 IKM、transcript 为 salt，用 `vlp:link:{c2s|s2c}:{key|nonce}:v2` 为 HKDF info 派生 32/12 字节。

配对码取 SHA256(`UTF8("vlp:link:pairing:v2") || transcript`) 的前三字节大端值 modulo 1000000，补齐六位，两端核对并确认。PAIR_CONFIRM=`{code:text6}`；PAIR_OK=`{paired:true}`。当前没有记住配对/后台重连免核对的分支。

PROVE=`{challenge:bstr32}`；OK=`{challenge,publicKey,sessionId:uint32,sessionEpoch:1,signature:bstrDER}`。证明摘要为 SHA256d(`UTF8("vlp:possession:v2\0") || transcript || publicKey || sessionId:u32BE || challenge`)；secp256k1 DER、low-S、直接签摘要。主机必须检查期望公钥、挑战、签名及 epoch，不能按 USB 端口判断同一个 Key。

认证记录每方向 seq 从 1 开始，严格连续；counter 从 0 开始且不回绕。nonce 为 96 位 baseNonce 加 counter modulo 2^96。AAD 为 `version:u8 || type:u8 || flags:0 || seq:u32BE || deviceRunId:u32BE || connectionId:u32BE`。密文尾含 GCM tag16；规范 CBOR 明文最多 896 字节。认证失败、乱序或重放关闭连接，不能跳帧续用密钥。

## 消息与操作

CBOR 仅接受确定长度、最短整数/长度、合法 UTF-8、长度优先再字节序的文本 map 键；键 1–31 字节、map 至多 24 对、容器深度至多 6；禁止浮点/tag/undefined/重复键/尾随字节。金额在 TS API 中为 bigint，线上为 CBOR uint64。

REQUEST=`{op:text,opVersion:1,body:value,requestId:uint32,binding,commitment:bstr32}`。
RESPONSE=`{requestId,binding,commitment,payload:value}`。
EVENT=`{kind,eventSeq:uint32,binding,payload}`；主机接收端已支持，当前设备没有业务事件生产器。

binding=`{sessionId:text,sessionEpoch:uint32,connectionId:uint32,deviceRunId:uint32}`，sessionId 为持有权证明 sessionId 的十进制文本。这是 **VLP USB 连接会话**，不等于外部 App 的业务会话。

业务承诺为 SHA256d(`UTF8("vlp:commit:v2\0" + profile + "\0") || profileVersion:u8 || canonicalCBOR(完整已核验核心)`)。主机不能挑选参与字段；设备先解析业务对象，再独立计算承诺。错误负载为 `{error:text-code}`，新版不沿用旧数字错误表。

控制操作仍通过 REQUEST：`system.ping` body={}、`system.query`/`system.cancel` body=`{requestId:uint32,commitment:bstr32}`、`system.lock`/`system.close` body={}。控制请求不消耗业务槽，也不产生业务签名；query/cancel 必须匹配目标承诺和当前绑定。锁定/关闭直接断链，调用方收到断开而非假成功。

设备一个活动业务槽、一个最近终态结果。接受请求维持单调 ID 水位；最近结果淘汰后旧 ID 仍拒绝执行。取消等待中的请求可以终止；执行中取消只返回真实执行状态。超时/失联为结果未知，主机不得自动重发签名或付款。主机排队由 Keymaster 适配层承担；SDK 有界 pending=32，busy 不能由无限重试掩盖。

当前链路等待超时 8 秒、主机每秒心跳/4 秒响应超时；握手阶段等候 60 秒，主机业务默认等候 120 秒。业务等候超时本身不证明设备未签名；必要时在仍有效的连接内查询。RocKey 产品控制器已接入滚动、读完后新按键长按批准、长按拒绝及累计增额；真机按钮和 USB 尚未验收。

支持 API、缺口与接入责任见 [SDK README](../../Coding/BSV8_VaultLinkProtocol/README.md)。


## 有界业务信封分片（0x224 Draft）

保持 REQUEST/RESPONSE/EVENT 三种帧类型。信封编码不超过 896 字节直接发送；超过时先以 canonical CBOR 编码整个信封，最多 32768 字节，逐段发送 `{fragment:{total:uint,offset:uint,hash:bstr32,data:bstr}}`。hash 为整个编码的 SHA256，data 每段 640 字节，末段可较短；每段仍是独立的 AES-GCM 认证记录，使用原连续序号和原帧类型。不得自行扩大帧或改变密码套件。

每方向一个重组槽，首段 offset=0；后续必须同帧类型、同 total/hash、精确连续 offset，非末段必须满 640 字节。自首段起最多 8 秒，完整 hash 验证后才解析、校验承诺或执行。乱序、重复、混用帧类型、篡改、超长及超时关闭会话；关闭擦除重组内容。实现串行发送完整消息，避免两条大信封交错；小控制消息可在重组期间接收，仍须逐记录认证。该上限覆盖当前标准交易和多数完整前序原文，不宣称支持任意尺寸交易。

软件同 Key 迁入能力：`0x232` 为本机 PIN 设置后的临时迁移连接，`0x233` 为已封装实际 Key 的提交恢复。严格 operation、profile、body、挑战证明和提交顺序见 `08-付款账本迁移.md`；不增加 USB 消息类型，不将临时传输 Key 当成钱包身份。
