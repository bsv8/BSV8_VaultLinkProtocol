# v2 支付核算与设备持久状态

日期：2026-10-09。用户已确定：只按输出计费，矿工费不占额度。普通 P2PKH 对外输出合计为 amount，本 Key 找零根据实际脚本识别并排除，矿工费另列基础事实。单笔与 App 会话累计均用整数 satoshi/uint64。费用池只能按经核验的对外付款新增量核算；Connect 2-of-2 与 BitFS 买方 2-of-3 的 fund/state 阶段已实现；其他脚本及角色不能回退任意摘要签名。

## 已实现的内部契约

PaymentPolicy 是唯一执行权威，通过 PolicyStore 原子保存快照；不能由主机输入 `withinLimit=true` 放行。App/plugin owner 与业务 sessionId 由可信适配层提供，支付 body 不接受自报 owner/已花金额。RocKey 产品适配已实现下面的 USB 渠道配置/会话操作；浏览器硬件绑定、迁移及全部资金入口仍未接通，不能据此宣布完整产品交付。

ChannelConfig：`id, owner, kind:app|plugin, network, paymentType, enabled, singleLimit:bigint, defaultSessionLimit:bigint, revision:uint32`；绑定当前 Key。既有渠道 owner/kind/network/type 不可改写，revision 严格 +1。首次登记、启用、提高单笔/默认累计额度须执行端确认；降低/撤销使未执行旧批准失效。

App Session：`id,owner,limit,used,revision,active`。同一 App 多渠道合并一个累计额度。defaultSessionLimit 属于 owner；配置某渠道时原子同步同 owner 的其他 App 渠道默认值并递增其 revision。新登记渠道由钱包适配器继承该 owner 已配置默认值，不能用零值重置。当前已建立会话的 limit/used 不因默认值修改而改变；载入旧冲突配置仍拒绝开会话。新会话须确认；同 ID/owner 且 active 的重复 open 幂等复用原 limit/used，已关闭 ID 不可复活。插件不创建累计会话。

Pending：`id,sessionId|null,channelId,amount,commitment,configRevision,sessionRevision,state`，其中 state 为 reserved/signed/unknown/released。预占先落盘，再签名；同 ID 永不二次预占/签署。仅确定未执行时可转 released 并释放占用，保留墓碑；已签与未知均不释放。不以广播成功作为计额条件。

快照为 `{version:2,key:compressedPublicKeyHex,channels,sessions,pending,pools}`，仅用于执行端内部存储，不是主机可任意恢复的 USB 输入。version 1 的旧快照只允许在没有 pools 字段时升级，保留原渠道、会话 used、签名/未知记录；不得当作空钱包重建。载入时校验 Key/引用/修订/计数一致性；任何失败停止自动支付，禁止内存回退。宿主必须提供防回滚、抗损坏、原子写入的真实设备存储；Node 文件适配只能用于参考实现，不能替代 ESP32 安全存储。

`quote` 同时列出 disabled/single-limit/session-limit；等于额度自动执行。超额 approval 绑定 requestCommitment、configRevision 和 sessionRevision。一次批准不改额度、不清 used；raiseSessionLimit 只改当前累计额度，并须足够覆盖 used+amount，不改未来默认或单笔额度。授权到执行之间再次检查配置/会话修订。

安全容量为 32 渠道、16 个保留会话、256 条支付记录、256 个费用池基线、持久编码最多 64 KiB。达到容量明确拒绝，不自动淘汰重放证据。**当前没有安全归档/回收协议；持续运行的产品接入需解决这项容量阻断，不能静默删除记录或重置预算。**

## P2PKH 实施范围

产品操作名 `tx.p2pkh-payment`，handler profile=`bsv-payment-context`、version=1。
body=`{rawTx:bstr,prevTransactions:bstr[],channelId:text,paymentId:text,sessionId:text|null}`；核验核心另加设备计算的 `amount:uint64`，主机计算承诺时必须使用相同解析规则。结果=`{signatures:bstrDERWith41[],amount:uint64}`。

仅 legacy 交易、所有输入由当前 Key 所有、空 scriptSig、全部输出 P2PKH、SIGHASH_ALL|FORKID=0x41。完整前序交易必须与 outpoint txid/vout 字节绑定；拒绝重复输入、错误 Key、未知脚本及负矿工费。目标最多 640 字节/4 输入/6 输出，前序单份最多 8192 字节，但整个 USB 信封编码最多 32768 字节，超过单条记录时按核心协议有界分片；没有压缩或自报输入证明替代路径。真实链上已确认/未花费状态由 Keymaster 负责，设备不声称验证网络共识。

设备从实际对象解释收款输出、找零、矿工费及超限原因；信用信息和业务叙述归 Keymaster。签名交付前写入 signed；写入失败不交付、不释放预占。新 wire 的费用池见下节，Channel、Local Secret 和迁移尚未支持；RocKey 复用已有三按钮 PIN 解锁，不在 USB 输入 PIN。未知操作返回 unsupported。

## 产品支付操作（能力 0x224，Draft）

共用 wire 2 的 REQUEST/RESPONSE、opVersion=1，金额为 CBOR uint64。绑定的 USB sessionId 与 body 中的 App 业务 sessionId 分开。下列 profile 的承诺核心为全部 body；交易操作还必须增加实际解析得到的 amount。操作能力声明不表示拥有尚未接通的迁移或费用池能力。

| op | profile | body | 成功 payload |
| --- | --- | --- | --- |
| payment.configure | payment-config | ChannelConfig 的九个字段 | `{configured:true,revision:uint32}` |
| payment.session-open | payment-session | `{sessionId:text,owner:text}` | `{opened:true,sessionLimit:uint64}` |
| payment.channel-read | payment-channel-read | `{channelId:text}` | 对应 ChannelConfig |
| payment.session-read | payment-session-read | `{sessionId:text}` | 对应 Session |
| tx.p2pkh-payment | bsv-payment-context | 见上文 P2PKH body | `{signatures:bstr[],amount:uint64}` |

设备配置操作目前仅接受 main/p2pkh，每次配置和新建 App 会话均显示设备确认页。读取不弹窗；返回一个对象而非无限列表，仍受 896 字节信封限制。App owner 取自已注册配置，不能靠交易请求另带自由 owner 改换身份。插件 sessionId 必须为 null，仅检查单笔；App sessionId 必须属于该 owner 的活动会话。

额度内不弹设备审核；超额显示实际收款地址和金额、找零、矿工费、单笔额度、已用累计及累计额度，由设备按钮批准/拒绝。地址从实际 P2PKH 脚本生成，主机标签不参与身份解释。一次批准不改额度；增额只改当前 App 会话累计。仅本 Key 输出的交易，对外 amount=0，矿工费仍解释且不占渠道额度；仍须验证输入、渠道、会话和请求重放。

参考 `P2pkhPaymentOperation` 的固定上下文模式仍使用 bsv-payment；产品双方必须明确选用 bsv-payment-context，不能混用两种承诺。0x221 是 SDK 参考能力，0x222 是之前 P2PKH 产品支付集合，0x223 是本轮含费用池的产品支付集合，均尚未登记为公开标准的最终分配。


## 2026-10-10：费用池 Profile 与持久增量账本

RocKey 产品 Draft 能力为 `0x223`，wire 仍为 2。新增操作：

| 操作 | Profile | body / 结果 |
| --- | --- | --- |
| `tx.feepool-connect` | `bsv-feepool-connect` v1 | 同支付 body，另加 `stage:fund|state`；结果同 P2PKH |
| `tx.feepool-bitfs` | `bsv-feepool-bitfs` v1 | 同上，当前签署者限定为 BitFS buyer |
| `payment.pool-read` | `payment-pool-read` v1 | `{poolId:text}` → `{poolId:text,paid:uint64,binding:bstr32|null}` |

签名请求不接受自报金额、历史累计、owner、sighash 或任意 digest。规范核心在 body 上增加执行端自己计算的 `amount:uint64`，进行 commitment 核验。签名均为 actual transaction 的 ALL|FORKID (`0x41`) low-S DER，客户端验证后才能使用。

Connect 脚本精确为 `OP_2 <server33> <client33> OP_2 OP_CHECKMULTISIG`；BitFS 精确为 `OP_2 <buyer33> <seller33> <arbiter33> OP_3 OP_CHECKMULTISIG`。所有 compressed key 必须有效且互不重复，顺序不可改。当前 Key 分别必须是 client/buyer。

`fund`：所有输入是当前 Key P2PKH，output[0] 是上述池脚本且金额为正，output[1] 是实际本 Key 找零。存入多签池只改变资金所在脚本，不是新增对外付款，amount=0；基础事实仍包含锁定金额、参与方、找零、矿工费。

`state`：恰好消费真实 funding outpoint[0]，脚本和金额来自完整前序交易，不能以客户端声明替代。Connect 输出固定 server/client P2PKH；BitFS 固定 buyer/seller/arbiter P2PKH，允许一个额外零值 `OP_FALSE OP_RETURN <canonical single push>` 付款证明。输出顺序、收款脚本、零值证明、unsigned input、负费用及重复输入均独立检查。

池 ID 为交易 outpoint 的内部字节序 txid 的 64 个十六进制字符 加 `:0`，不是 BitFS refund-template ID；binding 为实际池锁定脚本的 double-SHA256。`PoolState={id,binding,paid}` 保存累计对外输出总额。`Pending.pool={id,binding,previousPaid,paid}` 绑定预占。本次 amount=paid-previousPaid，降低累计或替换绑定拒绝。基线与渠道/会话预占在同一次原子保存中写入，且先于签名。同池有 reserved 请求时拒绝下一请求，避免前一请求未执行释放导致后续少计；过时基线拒绝。

相同累计的关池 amount=0，不重复计费；即使此前一次批准使 used 超过 limit，零新增付款也不触发累计超额原因。disabled 仍须明确批准。只有确定未执行的 reserved 请求可以回退池基线；签名、未知、重启、换会话、换渠道均不得回退。载入时核对未释放池增量之和等于池 paid，并核对每个引用和 binding。

`pool-read` 只供主机构造相同承诺；不能修改设备基线，也不是金额权威。不存在的池返回 paid=0/binding=null。现有状态的主机金额与设备核算不一致时拒绝签名。

上述实现不验证链上是否已广播/未花费，不新增网络确认要求。USB 896 字节完整信封限制保留；单输入、真实完整签名 FundingTx 的互通已经验证，较大证据仍可能超限。旧池若从未由新账本签署，首笔会按完整累计核算并要求相应批准，不把业务自报旧付款写入基线。卖方/仲裁协签、其他协议变体、自动归档、浏览器硬件切换和真机验收仍不在已交付范围。


## 标准单钥交易增量（2026-10-10）

`tx.standard-payment` / `bsv-standard-payment`，opVersion/profileVersion=1。body/结果与 P2PKH 相同，paymentType=`bsv.standard`。仅空 scriptSig 的 legacy 交易，最多 8192 字节、10 输入、32 输出，完整前序原文逐份核验 txid/vout。允许输入为当前 Key 的精确 P2PKH，或规范非空 data-push/DROP 前缀后精确 `<当前压缩公钥> CHECKSIG`；不执行任意脚本。输出为实际交易的一部分：能以同一规则证明本 Key 独占的输出算找零，其它输出全部算对外金额，并显示地址或脚本原文。每个输入仅签 ALL|FORKID=0x41。

费用池 fund 允许仅池输出，或池输出加本 Key P2PKH 找零。state 可显式带 `role:cosigner`，仅允许池内非付款方身份；仍须完整前序原文，paymentType=`feepool.{family}.cosigner`，不计作该协签方自己的对外支出，也不更新付款方的池基线。未声明 role 时仍严格为 payer。**BitFS Kind 2 卖方预签尚无完整 FundingTx，不满足此证据路径，未接硬件；不能以自报金额/脚本或摘要替代。**

Keymaster 软件 `session-cancel` 是宿主取消待批准申请的内部操作，未增加设备 wire 操作。它保留同一 Connect 连接的 limit/used，恢复连接不得借取消清额度；终止账本会话仍使用 session-close。USB 连接与 App 业务会话继续分别绑定。


## v3 本地秘密兼容增量（0x225 Draft，2026-10-10）

`local-secret.seal` / `local-secret.open`，opVersion=1；profile=`local-secret-v3`、profileVersion=1。仅正文内的 `scope,plaintext` 或 `scope,sealed`，全部参与承诺；不增加请求内的自由授权字段。继承 [Local Secret v3 配方](../profiles/04-local-secret.md) 的精确 HKDF/AES-GCM 配方和信封格式，不改旧密文版本。

- seal body=`{scope:text,plaintext:bstr1..512}`，结果为 v3 五字段信封。
- open body=`{scope:text,sealed:{version:3,keySource:active-key-hkdf-v1,saltHex,nonceHex,ciphertextHex}}`，结果=`{plaintext:bstr1..512}`。
- scope 是有效 UTF-8、1..95 字节，无控制字符或 DEL；salt/nonce 分别 16/12 字节，ciphertext 含末尾 tag16，拒绝未知字段、超长、篡改和认证失败。
- 长期 HKDF 派生密钥不导出；设备仅返回请求的解封明文。物理审核显示操作、scope、实际对象摘要，不显示秘密正文。0x226 增量支持本次决定、当前 USB 连接内的持续允许/持续否决和设备撤销，具体规则见下节。
- 解封操作不是支付，不改变支付额度。连接世代和完整请求承诺照常核验；临时编码/解密缓冲清理，最近结果按当前连接查询，替换或关闭时清理。

Keymaster 硬件代理已提供 sealLocalSecret/openLocalSecret；正式 C++ 实现已接 RocKey Endpoint。Keymaster 当前钱包仓储与生命周期尚未切换到硬件记录，不能把这一独立接入当作软件私钥已经迁出浏览器。Channel 与迁移仍未接入 wire 2。


## 本地秘密的持续决定与撤销（0x226 Draft）

请求、结果与承诺格式不变，主机不能传入 allow/deny/remember/grantId 来设置设备许可。决定来自设备实体操作：读完基础审核后短按 B 切换本次/会话模式，长按 B 允许，长按 A 否决。未选择会话模式时，允许/否决都只影响当前请求。

持续决定严格匹配操作（seal/open 分开）与完整 scope，归当前已认证的 USB 连接和当前 Key。后续每条请求仍校验独立对象承诺、范围、长度和密码格式；持续允许不跳过这些核验，持续否决也不执行密码操作。未初始化/断开/锁定/重启/换后端不继承决定。与付款单笔/累计额度账本分别管理，撤销本地秘密许可不重置或修改付款配置。

设备“会话决定”菜单显示选中的操作、允许/否决与完整 scope。A/C 选择前后项，短按 B 撤销当前项，长按 B 全部撤销，长按 A 返回。撤销允许或否决后，下次请求重新询问。执行前复核决定修订；撤销之后旧的已准备请求不能执行。当前最多 8 项持续决定，满时明确返回 grant-capacity，不自动淘汰否决或扩大许可；本次决定仍可使用。

这里只实现 v3 本地秘密的持续决定。Channel、迁移、支付生命周期及其它 Profile 仍须按各自施工状态判断，不能由此声明通用持续授权全部完成。真按键/屏幕/USB 验收尚未执行。


## App 预算恢复和指定关闭（0x227 Draft，2026-10-10）

新增 `payment.channel-list`，Profile `payment-channel-list` v1，body `{}`，返回本 Key 的 `ChannelConfig[]`（最多 32 项）。列表和单项读取不改变设备额度。Keymaster 以设备账本作为硬件模式唯一权威，不从浏览器设置覆盖 used，也不把软件批准弹窗复制到设备之前。

新增 `payment.session-close`，Profile `payment-session-close` v1，body `{sessionId:text}`，返回 `{closed:true}`。关闭指定已存在会话；重复关闭幂等。首次关闭 active=false、revision+1，保留 limit/used、付款记录、未知占用和墓碑。不存在会话报 invalid-session，关闭是撤权所以不要求实体批准。

USB 会话、App 会话独立。重载 TS/C++ Policy 保留持久 active/closed；reserved 转 unknown，绝不回退 used 或池累计。重复 payment.session-open 在同 owner 且 active 时返回原 limit、不再次批准/清零；已关闭或 owner 不同报 invalid-session。

主机取消待确认交易以 `ProtocolClient.submit` 实际请求 ID 和原 commitment 发送 system.cancel，绕过付款 FIFO。排队及前序读取中的同 App 请求也立即被本地撤权标记拒绝。session-cancel 只取消申请，session-close 另外关闭预算；已签/执行中/未知的占用不得释放。当前 Draft 0x227 包含上述操作与原 0x226 全部能力，旧固件不能作为同支持集接入。

### 有界安全归档（v3 bank，2026-10-10）

沿用同 Key 预算不回退、防重放与满额 fail closed 的既定要求。将已签或确定未执行释放的付款明细压缩为严格的 ID/完整记录哈希墓碑；未知或正在预占的付款不归档。活跃会话已消费累计、池 paid 基线与已归档累计分别保留，读取必须核对明细与累计。关闭会话仅在没有未知/预占记录时归档，其 ID 与完整关闭记录摘要永久防复活。v3 bank 携带全部墓碑与累计，双向迁移不丢弃；v2 保持已有格式直至首次实际归档。归档自身有界，满额继续明确拒绝，不以散列碰撞、过滤误判、删除墓碑或重置基线换取容量。


v3 根字段精确为 `version:3,key,channels,sessions,pending,pools,archive`。channels/pending 沿用 v2；每个活跃或尚需保留明细的 session 增加 `archivedUsed:uint64`，pool 增加 `archivedPaid:uint64`。`archive` 精确为 `{payments:array,sessions:array}`：

- payments 项为 `{idHash:bstr32,recordHash:bstr32}`；idHash 是付款 ID 的 UTF-8 SHA-256；recordHash 是含 `pool:null` 或完整 pool 的原 signed/released 付款记录规范 CBOR 的 SHA-256。
- sessions 项为 `{idHash:bstr32,recordHash:bstr32,record:{id,owner,limit,used,revision,active:false,archivedUsed:used}}`。保留完整关闭回执，使迁移前活跃、迁移后关闭并归档的会话也能核对 owner、累计与修订；两种 hash 按相同配方核验。
- 两种归档数组分别最多 512 项，同类 ID hash 不重复，不能与活跃明细同 ID。持久 bank 仍最多 65536 字节；达到字节上限可能先于条数上限，均拒绝继续执行。
- 单笔预占前，明细达到 128 项时尝试归档终态；明细硬上限仍为 256，未知/预占不会被移除。新会话前达到 16 项时尝试归档关闭会话，其有关终态付款先归档；未知/预占仍使会话保留。归档写入必须成功才继续。
- `session.used = archivedUsed + 保留的 reserved/signed/unknown 金额`；`pool.paid = archivedPaid + 对应保留金额`。released 不算消费。归档不改变 used/paid、限额或修订，不释放签名和未知结果的金额。
- 两端重载、规范编码、迁移持有权核验和硬件账本 continuation 都支持 v2/v3；旧归档必须完整保留。付款删除仅允许有原不可变终态记录的精确回执；会话删除仅允许有完整可核验关闭回执，累计和修订不回退。其它删除、unknown 丢失或 used/paid 重置都拒绝。
- C++ Policy 的 SHA-256 适配由产品注入真实 `vaultlink::sha256`；缺少适配不能读取 v3，也不能归档。CBOR 只有显式 65536 字节的 bank 路径允许 512 项数组；USB wire 的数组、消息和分片上限不变。

可复现宿主验证：SDK `test/payment-archive.test.mjs` 使用原子磁盘 bank 与实际 C++ Policy/mbedTLS，覆盖累计、防重放、未知保留、会话后来关闭的迁移连续性、池基线、篡改和有限容量。该证据不等于实体 Flash 掉电或最大容量下的设备 RAM 验收。
