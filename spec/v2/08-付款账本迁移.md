# 付款账本迁移与私钥迁回的提交次序

状态：公开 bank、双方 journal、硬迁软导出/独立擦除及回执恢复代码已实现；软件同 Key 迁入新设备、阶段恢复和产品向导已实现。实体 USB、按键、重启和 Flash 掉电尚未验收。

## 公开账本编码

`encodePaymentPolicy` / `decodePaymentPolicy` 使用设备 Policy v2/v3 的规范 CBOR bank。根字段精确为 `version:2, key:text, channels:array, sessions:array, pending:array, pools:array`，不接受额外字段。最大 65536 字节；保留全部单笔/默认会话限额、当前/已关闭会话的累计数、配置与会话 revision、付款承诺/状态，以及费用池累计基线。金额使用 uint64，不能经 JS 浮点数或十进制近似转换。bank 不含私钥、PIN 或软件密码。

首次安全归档后使用 v3 根字段及归档累计/关闭回执，精确格式见 [支付与持久状态](./02-支付与持久状态.md)。归档不能在迁移时省略或降级回 v2。

SDK 独立检查钱包公钥、owner、会话引用、累计值与付款状态的一致性。向硬件迁移前必须检查硬件支持的 network/paymentType 和容量。未知或已签付款不能作为迁移中的空闲额度；存在 `reserved` 时先停止并结清正在执行的付款，不能迁移一半的签名。

## 已实现操作：payment.policy-export

Profile：`payment-policy-export` v1。请求 body 精确为 `{offset:uint, length:uint}`。`length` 为 1–8192，`offset` 必须小于完整 bank 的大小。返回 `{offset:uint, size:uint, sha256:bstr32, chunk:bstr}`；`size` 为 1–65536，`chunk` 是对应范围的真实 bank 字节。

这是已认证 USB 会话中的公开设置/账本读取，无私钥导出，不需要实体签名许可。宿主占用自己的业务 FIFO 直到全部分块读完；逐块检查 offset、总大小、范围及完整 bank SHA-256 的一致性，再对重组内容核验 SHA-256、规范编码和当前钱包身份。任一块失败或读取期间 bank 改变，不能采用半份账本或默认空账本。

## 宿主迁移 journal 与恢复边界

持久阶段为 `prepared → device-committed → local-committed → complete`。公开 journal 保存迁移 ID、同一钱包世代/公钥、源/目标后端、源记录 revision/hash、付款 bank hash/原浏览器账本 revision、阶段及目标记录 hash；不保存私钥、PIN、密码或软件回退副本。

准备阶段绑定实际源记录和付款账本。设备确认必须对应同一迁移及 bank。浏览器提交使用一个 IndexedDB 事务，同时替换 `key.json`、付款账本与 `local-committed` journal，条件比较源 Key、meta、账本及 journal 的 revision。异步提交时不能更换身份或覆盖其它标签页的新记录。任一条件失败，整个事务回滚。

冷启动遇到未完成或损坏的 journal 必须进入恢复状态，不能普通解锁原后端、自动创建新 Key 或默认回退另一后端。`device-committed` 之后不能只删除浏览器 journal 当作取消；设备可能已经持有迁移 Key，必须核对设备实际状态再恢复。

## 已完成迁入后的重连核验

浏览器保留的公开付款账本只能作为同 Key 迁入的基线，不能成为硬件执行时的第二个额度权威。重连必须有 `complete`、目标为 hardware、同公钥及钱包世代的本地迁移 journal，且浏览器基线的规范 bank SHA-256 与 journal 一致。

`assertPaymentPolicyContinuation` 独立检查设备当前 bank 对该基线的继续性：原渠道的 owner/kind/network/paymentType 保持，revision 不退回，同 revision 的额度/启用不能改变；原会话累计及 revision 不退回，关闭会话不复活，同 revision 的总限额不改变；所有原付款 ID、承诺、金额、配置/会话修订和费用池绑定继续保留，已消费/未知付款不退回空闲，released 墓碑不复活；池累计基线不降低。新活动和经用户批准的更高配置修订允许继续，但不存在有效 journal、空账本、删旧会话或删付款墓碑均拒绝。

这是普通重连的完整性门禁，不能证明私钥已经迁移，也不提供导入、自动完成迁移或归档删除权限。

## 2026-10-10 用户确认：硬迁软后擦除

私钥迁回软件环境时，先在专用 Worker 验证它与当前钱包公钥一致，用新软件密码生成 KeyHold；浏览器原子提交成功之后，用户再在硬件上独立确认擦除旧私钥。硬件擦除成功并得到恢复可核对的结果之后，才结束迁移并启用软件后端。不得在浏览器可恢复提交之前擦除硬件唯一副本，也不得由普通 App 或注销操作自动触发擦除。

设备重新验 PIN 必须经过同一个持久失败计数/等待门禁。验 PIN 失败或 I/O 失败清空旧 RAM Key。擦除必须检查持久文件及 tmp 副本删除、设备秘密轮换和状态写入结果；失败不能向宿主报告“已擦除”，不能直接跳到创建新身份界面。

私钥传输仍使用原 USB 加密通道，不增加信用服务、业务 Markdown 或主机 PIN。私钥返回不能进入通用结果查询/重放缓存；丢失导出响应需要重新实体批准，不通过 query 再次取得私钥。RocKey 已实现本地菜单开启、重新 PIN、一次性实体导出和结果清理，公布 migration.export；migration.import 尚不公布。


## 设备公开 journal（Draft 0x22f）

`migration.status` / `key-migration-status` v1：body 精确为 `{}`，返回 `{migration:null|record}`。record 精确九字段：

| 字段 | 编码 / 含义 |
| --- | --- |
| version | uint，固定 1 |
| id | text，小写 UUID，迁移编号 |
| walletGeneration | text，小写 UUID，浏览器已有身份世代 |
| publicKey | bstr33，原业务公钥 |
| sourceHash | bstr32，浏览器源 key.json 原始字节 SHA-256 |
| policyHash | bstr32，源规范付款 bank SHA-256 |
| direction | text，to-hardware / to-software |
| phase | text，staged / device-committed / host-committed / erasing / erased / complete |
| targetHash | null 或 bstr32，浏览器目标记录 SHA-256 |

`targetHash` 在 staged/device-committed 必须为空，后续必有；to-hardware 不允许 erasing/erased。journal 不包含私钥、PIN、软件密码或许可。设备使用有 CRC/单调 generation 的原子记录，损坏、旧版迁移文件及存储失败均拒绝继续。读取记录必须与浏览器 journal 的完整绑定核对；读到某个阶段本身不授予任何密钥操作。

## 硬迁软私有操作（Draft 0x230）

| 操作 / Profile v1 | 精确 body | 精确成功结果 |
| --- | --- | --- |
| migration.export / key-migration-export | `{id, walletGeneration, sourceHash:bstr32, policyHash:bstr32}` | `{privateKey:bstr32, migration:record}` |
| migration.host-commit / key-migration-host-commit | `{id, targetHash:bstr32}` | `{migration:record}`，host-committed |
| migration.erase / key-migration-erase | `{id, targetHash:bstr32}` | `{migration:record}`，erased |

export 先要求用户在本机菜单开启，再重新输入真实 PIN、读完摘要/风险并长按仅本次确认。持续许可与 USB 字段不能替代。输出前先落盘 staged→device-committed；私钥只走原认证加密 USB，并排除 query/replay 的结果缓存。响应丢失后只能重新本地开启和重新批准导出。

Worker 独占迁移前先排空已有钱包 I/O；整个流程禁止新业务 I/O/签名。收到私钥后实际派生核对公钥，用新软件密码生成 KeyHold，并实际解密回读核对。随后一个 IndexedDB 事务写 KeyHold、完整额度账本和 local-committed journal。私钥及回读副本在 finally 清零，Window/插件的返回 DTO 不包含私钥。

host-commit 只能由真实浏览器提交后发送，且只记录公开目标承诺，**不触发擦除**。erase 必须另一次 PIN 和实体确认；先写 erasing，再检查真实文件删除/秘密轮换/失败状态保存及清除所有 RAM 私钥副本，最后写 erased。任何步骤失败不能报告成功。收到与浏览器提交完全一致的擦除回执之后才把 host journal 标为 complete；软件钱包随后锁定，以新密码重新解锁。

设备仍有旧 Key 时，恢复重新验证同一旧 Key 的持有权，并核对同一 journal；恢复连接不安装普通钱包 Root 或付款能力。prepared/device-committed 重新导出仍需本地开启和新 PIN。local-committed 恢复只继续既有目标的 host-commit/erase，不重写目标密文或再次导出。

## 旧 Key 已不存在时的回执恢复（Draft 0x231）

设备已经删除 Key 时不能再证明旧私钥持有权，不能伪造这种证明或把另一个 Key 当成迁移成功。专用恢复运行时只在 Key 文件确实不存在，且持久记录为 to-software 的 erasing/erased/complete 时启动。它用 RAM 临时身份完成原 USB 加密与实体配对；临时公钥绝不保存为钱包身份，也不授予签名、付款、私钥导入/导出或普通软件解锁。

浏览器必须已存在经仓储完整校验的 local-committed journal、同公钥 KeyHold 和实际 bank；逐字段核对设备恢复记录，包括目标 KeyHold hash。该连接只开放 `migration.status`、`migration.recover-erased` / `key-migration-recover-erased` 和 `migration.complete` / `key-migration-complete`，后两者 body 都是 `{id,targetHash:bstr32}`，返回 `{migration:record}`。

erasing 表示旧 Key 文件已不存在但剩余清理可能尚未完成：设备要求独立实体仅本次确认，执行真实清理并持久化 erased。此时旧 PIN 封装可能已经删除，因此不假装能再次验证旧 PIN；存在任何 Key 文件（包括损坏文件）时绝不允许这条路径。erased 回执已持久化时只核对结果，不重复要求擦除。浏览器实际完成 journal 后可发送公开 complete；它没有创建/重置设备身份的权限。

设备保留回执。用户只有确认浏览器迁移完成后，才能从设备本地提示进入独立长按重置，删除回执并设置新钱包；USB 恢复命令不会自动创建新 Key。实体配对及记录核对证明的是这条受限恢复连接，不是已不存在的旧私钥持有权；不能作为普通硬件钱包重新激活依据。

## 软件同 Key 迁入：临时配对、账本暂存与实际持有权（2026-10-10）

空 RocKey 在本机重复设置 PIN 后选择“导入”；PIN 仅在设备 RAM 暂存，取消、断开、超时、重启清零。已有迁移暂存记录只能恢复同一迁移；已存在任何 Key（含损坏记录）的设备拒绝导入替换。普通新建和恢复备份不得绕过迁移记录创建另一身份。

临时导入连接能力 `0x232` 只运行迁移端点，其握手公钥不等于钱包公钥，不得持久化为 Keymaster 的 Key。导入已封装 Key 的重连能力 `0x233` 在原 PIN 解锁后提供同一组公开恢复/实际持有权证明。导入后的临时连接不转成普通钱包连接；业务激活必须重新连接，挑战验证实际钱包公钥。双方沿用 wire 2 的加密消息与取消/查询机制。

| operation / commitment profile | 严格 body | 成功结果 |
| --- | --- | --- |
| `migration.import-begin` / `key-import-begin` | `id, walletGeneration, publicKey:bstr33, sourceHash:bstr32, policyHash:bstr32, size:uint(1..65536)` | `{migration}` |
| `migration.import-stage-status` / `key-import-stage-status` | `id` | `{size:uint, total:uint, sha256:bstr32}`，size 为已落盘字节数，hash 为该前缀 |
| `migration.import-stage` / `key-import-stage` | `id, offset:uint, chunk:bstr(1..8192)` | 同 stage-status |
| `migration.import-key` / `key-import-key` | `id, privateKey:bstr32, challenge:bstr32` | `{migration, signature:bstr}`；禁止通用查询缓存此一次性操作结果 |
| `migration.import-proof` / `key-import-proof-request` | `id, challenge:bstr32` | 同 import-key，仅证明设备已实际封装并经 PIN 解锁的业务 Key |
| `migration.import-commit` / `key-import-commit` | `id, targetHash:bstr32` | `{migration}`，to-hardware 达到 complete |

begin 建立同一 9 字段公开 journal 的 staged 阶段并固定 bank 大小。stage 只允许续写；重复分块必须与已落盘范围逐字节一致，禁止修改前缀或以空数据清账本。完整 bank 必须匹配原 policyHash、同一公钥、严格规范 v2/v3 付款格式和设备容量；存在 reserved 不导入，unknown、已消费、关闭会话与池基线完整保留。缺失、损坏、落盘失败不得当成空账本。

import-key 必须由本机新的 PIN 输入验证、读完摘要与独立实体长按确认；不提供持续许可/否决、不接受 USB PIN 或 approve 字段。写入顺序为：完整账本落盘 → 用本机 PIN 与设备保护秘密封装私钥 → 用实际 KeyStore 解锁验证 → journal device-committed → 实际业务私钥的挑战签名。导入设备只接收 32 字节私钥，不接收或保留浏览器软件密码封装。

挑战签名是严格 low-S DER，签名摘要为 `commitment("key-import-proof", 1, {id, publicKey, sourceHash, policyHash, challenge})`。challenge 由 Worker 每次新生成 32 字节；SDK 按原软件钱包公钥验签，拒绝临时传输私钥签出的替代证明。staged 公开阶段不等于私钥已导入。封装已写入而公开阶段尚未更新的提交点，在实际 PIN 解锁并核验同一 bank/公钥后，由 scoped import-proof 补写 device-committed，不能重导或新建。

浏览器先保留原 KeyHold 与业务数据，核验实际持有权后进入 device-committed，再在一个 IndexedDB CAS 事务中替换同身份的硬件公开记录、完整账本和 local-committed journal。之后 import-commit 使设备 host-committed → complete，浏览器 finish，钱包锁定。local-committed 恢复只做新的实际持有权挑战与同 targetHash 的公开提交，禁止重新解密/重传源私钥。

complete journal 是历史提交回执。它仍约束公钥、钱包世代与后端；正常改名、改密码及后续软件付款可以改变当前 Key/账本字节，不应再要求它们等于历史提交 hash。prepared/device-committed/local-committed 阶段仍严格绑定当时的源/目标字节及账本。
